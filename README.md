# Система управления бизнесом — микросервисы

Backend-система управления бизнесом на FastAPI: регистрация компаний и сотрудников,
организационная структура, задачник. Реализована как три независимых микросервиса,
обменивающихся событиями через Kafka.

## Архитектура

| Сервис | Порт | Ответственность |
|---|---|---|
| `auth-service` | 8000 | Регистрация компаний и сотрудников, аутентификация, выдача JWT, личные данные, оркестратор саги |
| `org-service` | 8002 | Организационная структура (дерево подразделений на `ltree`), должности, руководители |
| `tasks-service` | 8003 | Задачи, участники, статусы |

У каждого сервиса **своя база данных**. Прямых обращений к чужим таблицам нет —
только события через Kafka. Данные о компаниях и сотрудниках `org-service` и
`tasks-service` держат у себя в виде минимальной реплики, наполняемой из событий
`auth-service`.

```
                 ┌──────────────┐
   client ──────▶│ auth-service │──── company.created ────┐
                 │              │──── employee.created ───┤
                 │  (+ saga)    │──── employee.updated ───┤
                 └──────┬───────┘──── employee.registered │
                        │                                 ▼
                   saga-commands                    ┌───────────┐
                   saga-replies  ◀──────────────────│   Kafka   │
                        │                           └─────┬─────┘
              ┌─────────┴──────────┐                      │
              ▼                    ▼                      │
      ┌──────────────┐     ┌───────────────┐              │
      │ org-service  │     │ tasks-service │◀─────────────┘
      └──────────────┘     └───────────────┘
```

### Процессы

Каждый сервис запускается как несколько независимых процессов из одного образа:

| Процесс | auth | org | tasks |
|---|---|---|---|
| HTTP API (`uvicorn app.main:app`) | ✅ | ✅ | ✅ |
| Outbox publisher (`app.outbox.run_publisher`) | ✅ | ✅ | ✅ |
| Inbox consumer (`app.inbox.run_consumer`) | — | ✅ | ✅ |
| Saga (`app.saga.run_saga` / `run_saga_consumer`) | ✅ оркестратор | ✅ исполнитель | ✅ исполнитель |
| Saga watchdog (`app.saga.run_watchdog`) | ✅ | — | — |

Фоновые воркеры вынесены в отдельные процессы, а не запускаются через `lifespan`
FastAPI: публикация событий и обработка команд — не HTTP-обработчики, у них
собственный жизненный цикл и независимое масштабирование.

## Быстрый старт

Требуется Docker с плагином Compose.

```bash
cp .env.example .env      # обязательно: без секретов compose не стартует
docker compose up --build
```

Поднимутся: три Postgres, Kafka (KRaft, без Zookeeper), MailHog и контейнеры
приложений. Миграции применяются отдельными контейнерами `*-migrate`, остальные
процессы стартуют только после их успешного завершения.

| Что | Адрес |
|---|---|
| auth-service Swagger | http://localhost:8000/docs |
| org-service Swagger | http://localhost:8002/docs |
| tasks-service Swagger | http://localhost:8003/docs |
| MailHog (письма с инвайтами) | http://localhost:8025 |

Логи отдельного процесса: `docker compose logs -f auth-saga`.

Секреты (`JWT_SECRET`, пароли БД) объявлены в compose через `${VAR:?...}` и не имеют
значений по умолчанию — запуск без настроенного `.env` прерывается с явной ошибкой,
а не уходит в работу с секретом из репозитория.

### Проверочный сценарий

1. `GET /auth/api/v1/check_account/{email}` — код подтверждения придёт в MailHog
2. `POST /auth/api/v1/sign-up/` — подтвердить владение почтой
3. `POST /auth/api/v1/sign-up-complete/` — создать компанию и администратора
4. `POST /auth/api/v1/login/` — получить JWT
5. `POST /org/api/v1/struct-adm/root` и `POST /org/api/v1/positions/` — создать
   подразделение и должность
6. `POST /auth/api/v1/employees/` с `struct_adm_id` и `position_id` — завести сотрудника
7. `POST /auth/api/v1/employees/register/` — сотрудник задаёт пароль, стартует сага
   онбординга: привязка к подразделению в `org-service` и приветственная задача
   в `tasks-service`

Готовая коллекция запросов — в папке `requests/`.

## Контракты событий

Все сообщения передаются в едином конверте (envelope):

```json
{
  "event_id": "uuid",
  "event_type": "company.created",
  "schema_version": 1,
  "producer": "auth-service",
  "payload": { }
}
```

Ключ партиционирования Kafka — `aggregate_id` (обычно id сотрудника или компании).
Это гарантирует, что события одной сущности обрабатываются в порядке публикации.

### Топики

| Топик | Кто пишет | Кто читает | Назначение |
|---|---|---|---|
| `auth-events` | auth | org, tasks, saga | Доменные события auth-service |
| `org-events` | org | — | Доменные события org-service |
| `tasks-events` | tasks | — | Доменные события tasks-service |
| `saga-commands` | оркестратор | org, tasks, auth | Команды саги исполнителям |
| `saga-replies` | org, tasks, auth | оркестратор | Ответы исполнителей |
| `dlq` | все | — | Сообщения, которые не удалось обработать |

Команды и доменные события намеренно разведены по разным топикам: у них разная
семантика (инструкция конкретному адресату против уведомления «для всех, кому интересно»)
и разный смысл ключа партиционирования. Целевой топик хранится в колонке
`outbox_message.topic` — publisher не вычисляет его по имени события, а берёт готовым.

### Доменные события

| Событие | Издатель | Подписчики | Payload |
|---|---|---|---|
| `company.created` | auth | org, tasks | `company_id`, `name` |
| `employee.created` | auth | org, tasks | `employee_id`, `name`, `surname`, `company_id` |
| `employee.updated` | auth | org, tasks | `employee_id`, `name`, `surname` |
| `employee.registered` | auth | saga | `employee_id`, `company_id`, `invite_id`, `struct_adm_id`, `position_id` |
| `task.status_changed` | tasks | — | `task_id`, `company_id`, `old_status`, `new_status`, `changed_by`, `responsible_id` |

`task.status_changed` пока не имеет подписчиков — он предназначен для
`notification-service`, вынесенного в бонусную часть.

### Команды и ответы саги

| Команда | Исполнитель | Ответ (успех) | Ответ (провал) |
|---|---|---|---|
| `org.assign_employee` | org | `org.employee_assigned` | `org.employee_assignment_failed` |
| `tasks.create_welcome_task` | tasks | `tasks.welcome_task_created` | `tasks.welcome_task_failed` |
| `org.unassign_employee` | org | `org.employee_unassigned` | — |
| `auth.invalidate_invite` | auth | `auth.invite_invalidated` | — |

Компенсирующие команды ответа о провале не имеют: неудачная компенсация —
случай для ручного разбора, а не для нового витка отката.

## Надёжность доставки

### Transactional Outbox

Бизнес-изменение и запись события коммитятся одной транзакцией. Отдельный процесс
publisher забирает накопленные события и публикует их в Kafka.

**Захват пачки.** Publisher не просто читает строки, а атомарно переводит их в
статус `PROCESSING` одним `UPDATE ... RETURNING` с `FOR UPDATE SKIP LOCKED` в
подзапросе. Два параллельно работающих publisher'а не могут захватить одно событие:
блокировки на чтении недостаточно, потому что она снималась бы до похода в Kafka.

**Зависшие захваты.** Если publisher упал между захватом и отправкой, события
остались бы в `PROCESSING` навсегда. Перед каждым циклом просроченные захваты
возвращаются в очередь.

**Ретраи.** Неудачная публикация переводит событие в `FAILED` и назначает
`next_retry_at` с экспоненциально растущей задержкой (2, 4, 8, 16 секунд).
Publisher забирает такие события наравне с новыми, когда время наступило.

**DLQ.** После исчерпания лимита попыток событие отправляется в топик `dlq`
и помечается терминальным статусом `DEAD` — оно остаётся в таблице для разбора,
но больше не подбирается к публикации.

**Гарантии продюсера.** `acks="all"` и `enable_idempotence=True`: сообщение
считается отправленным только после подтверждения всеми синхронными репликами,
а повторы на уровне транспорта отбрасываются брокером. В текущем compose брокер
один, поэтому практической разницы нет — настройка описывает требуемую гарантию,
а не текущую конфигурацию кластера.

### Idempotent Consumer (Inbox)

Перед обработкой события консьюмер проверяет `event_id` в таблице `inbox_message`.
Отметка об обработке и бизнес-эффект коммитятся одной транзакцией, поэтому
повторная доставка не даёт повторного эффекта.

Offset коммитится только после успешной обработки. При ошибке позиция чтения
возвращается к последней подтверждённой (`seek_to_committed`) — без этого
незакоммиченное сообщение не было бы перечитано в рамках текущей сессии,
а следующий успешный commit сдвинул бы offset за его пределы.

### Idempotency-Key

Небезопасные операции защищены middleware: при повторном запросе с тем же
заголовком `Idempotency-Key` возвращается сохранённый ответ первой успешной
обработки, помеченный `Idempotency-Replayed: true`. Заголовок необязателен —
без него запрос обрабатывается обычным образом. Неуспешные ответы не сохраняются.

## Сага онбординга

Реализована через **оркестрацию**. Оркестратор живёт в `auth-service/app/saga/`,
хранит состояние в таблице `saga_instance` и знает весь сценарий целиком.
Сервисы-исполнители о саге не знают — они получают команды, выполняют действие
и публикуют ответ.

### Успешный путь

```
employee.registered
      ↓
[оркестратор] создаёт saga_instance, шаг = ORG_ASSIGN_SENT
      ↓ org.assign_employee
[org] привязывает сотрудника к подразделению и должности
      ↓ org.employee_assigned
[оркестратор] шаг = TASK_CREATE_SENT
      ↓ tasks.create_welcome_task
[tasks] создаёт приветственную задачу
      ↓ tasks.welcome_task_created
[оркестратор] статус = COMPLETED
```

### Компенсации

Провал на первом шаге (подразделение удалено, чужая компания) — откатывать в
`org-service` нечего, компенсация ограничивается пометкой инвайта недействительным.

Провал на втором шаге — сначала откатывается привязка в `org-service`
(`org.unassign_employee`), затем помечается инвайт. Статус саги проходит
`COMPENSATING → COMPENSATED`.

### Guard переходов

Каждый обработчик ответа проверяет, что сага находится на ожидаемом шаге. Это
защищает от повторной доставки ответа (Kafka гарантирует at-least-once) и от
ответов, пришедших не в свою очередь.

### Гонка с репликацией

Команда `org.assign_employee` может прийти раньше, чем `org-service` обработает
`employee.created` — топики разные, порядок между ними не гарантирован. В этом
случае исполнитель **не отвечает провалом** (иначе запустилась бы ненужная
компенсация), а поднимает исключение: offset не коммитится, позиция чтения
откатывается, и команда обрабатывается повторно, когда реплика появится.

Число таких попыток ограничено. Если реплика так и не пришла, команда уходит
в DLQ и offset коммитится — иначе одно потерянное событие заблокировало бы
обработку всех последующих команд в той же партиции.

### Watchdog

Исполнитель может не ответить вовсе: упасть, потерять сообщение или отбраковать
команду в DLQ. Без внешнего контроля сага осталась бы в `RUNNING` навсегда.

Отдельный процесс периодически ищет саги, не менявшиеся дольше таймаута,
и запускает для них компенсацию, соответствующую текущему шагу. Саги, зависшие
уже во время компенсации, помечаются `FAILED` — дальше требуется ручной разбор.

## Паттерны и где они в коде

| Паттерн | Где |
|---|---|
| **Repository** | `app/repositories/` — `BaseRepository` с общими операциями, наследники с доменными запросами |
| **Service Layer** | `app/services/` — вся бизнес-логика; эндпоинты только распаковывают запрос и вызывают сервис |
| **Unit of Work** | `app/uow.py` — асинхронный контекстный менеджер: одна сессия на запрос, commit/rollback, все репозитории на общей сессии |
| **Dependency Injection** | `UnitOfWork` передаётся в сервисы через конструктор; границу транзакции определяет вызывающий код, а не сервис. HTTP-зависимости через `Depends` |
| **DTO / Schema** | `app/schemas/` — Pydantic-модели отдельно от ORM; сервисы принимают примитивы, а не схемы, и не знают о HTTP |
| **Router Composition** | `app/api/v1/router.py` — префикс и версия задаются один раз, доменные роутеры знают только свою часть пути |
| **Depends для сквозных задач** | `app/api/dependencies.py` — `get_current_user` разбирает JWT и отдаёт контекст пользователя |
| **Centralized Error Handling** | `app/core/error_handlers.py` — доменные исключения маппятся в HTTP в одном месте, эндпоинты свободны от `try/except` |
| **Transactional Outbox** | `app/core/outbox.py` (сборка конверта), `app/outbox/publisher.py` (захват пачки, ретраи, DLQ) |
| **Idempotent Consumer / Inbox** | `app/services/inbox_service.py` — проверка `event_id` в `inbox_message`; отметка и бизнес-эффект в одной транзакции |
| **Idempotency** | `app/api/idempotency.py` — middleware, возвращающее сохранённый ответ по `Idempotency-Key`. Плюс guard-переходы статусов (`invite`, `task`, `saga_instance`) |
| **Adapter / Gateway** | `app/adapters/` — `KafkaProducerAdapter`, `KafkaConsumerAdapter`, `EmailSender`. Знание об aiokafka и SMTP не выходит за их пределы |
| **Saga / Orchestrator** | `auth-service/app/saga/onboarding_saga.py` — сценарий и компенсации; `watchdog.py` — контроль зависших саг; `*/app/saga/command_handlers.py` — исполнители |
| **Event Contracts** | `app/core/event_types.py` — enum типов событий вместо строк; `app/schemas/event_envelope.py` и `event_payloads.py` — валидация конверта и полезной нагрузки |

## Тесты

Требуется запущенный Postgres (проще всего — `docker compose up -d auth-db org-db tasks-db`).

```bash
cd auth-service && uv run pytest -v
cd org-service && uv run pytest -v
cd tasks-service && uv run pytest -v
```

Тестовые базы (`auth_db_test` и т.д.) пересоздаются на каждом прогоне, схема
накатывается **через Alembic**, а не через `create_all` — тесты проверяют ту же
схему, что и рабочее окружение, и ловят расхождение между моделями и миграциями.

Покрыты обязательные сценарии: регистрация компании, создание подразделения через
`ltree`, CRUD задачи, идемпотентность операций, обработка дубля события в inbox.
Дополнительно — права по ролям, межкомпанийная изоляция, guard переходов статусов,
запись событий в outbox с проверкой контракта конверта.

## Известные ограничения

Осознанные упрощения, принятые для учебного проекта:

- **Реплика пользователя хранит одну компанию.** Человек может состоять в нескольких
  компаниях (`member` в auth-service это допускает), но в репликах `org`/`tasks`
  сохраняется компания из первого события. Оргструктура и задачи такого сотрудника
  видны только в одной компании.
- **Выбор компании при логине.** Если пользователь состоит в нескольких компаниях,
  без явного `company_id` в запросе выдаётся токен для самого раннего членства.
- **Симметричный ключ JWT (HS256).** Один общий секрет во всех сервисах: технически
  любой из них может выпустить валидный токен. В продакшене здесь был бы RS256
  с приватным ключом только у auth-service.
- **Счётчик попыток ожидания реплики хранится в памяти консьюмера.** После
  перезапуска отсчёт начинается заново. Приемлемо, потому что при рестарте реплика
  с высокой вероятностью уже подтянулась.
- **Нет автоматической обработки DLQ.** Сообщения накапливаются в топике и в
  таблице `outbox_message` со статусом `DEAD`, разбор ручной.
- **Один брокер Kafka в compose.** `acks="all"` при `replication_factor=1`
  эквивалентен `acks=1` — настройка задаёт требуемую гарантию на случай
  многоузлового кластера, но здесь не проверяется.
