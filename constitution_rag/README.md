# Цитатник Конституции РФ — RAG-сервис на FastAPI

Сервис отвечает на вопросы на естественном языке **точными цитатами из Конституции Российской Федерации** со ссылкой на статью и часть. Если подключена LLM, он дополнительно собирает из найденных цитат связный ответ, но сами цитаты всегда берутся из базы, а не из текста модели.

> ⚖️ Сервис возвращает выдержки из текста Конституции и **не является юридической консультацией**.
> Индексируется редакция 1993 года с поправками, одобренными 1 июля 2020 года.

## Возможности

| Эндпоинт | Что делает |
|---|---|
| `GET /search?q=...&k=5` | поиск цитат без LLM: фрагменты со ссылками и скорами |
| `GET /articles/{number}` | точная выборка статьи по номеру (`3`, `67.1`), без векторного поиска |
| `POST /ask` | цитаты + связный ответ модели с обязательными ссылками `[Статья N, часть M]` |
| `GET /healthz` | процесс жив |
| `GET /readyz` | индекс построен (503, если пуст), показывает, включена ли LLM |

Ключевые свойства:

- **Структурное чанкование** по главам, статьям и частям вместо нарезки по N символов.
- **Порог «не найдено»**, подобранный по метрикам: на вопросы вне темы сервис честно отвечает, что ответа нет, и **не вызывает LLM**.
- **Точная выборка по номеру**: «что говорит статья 15» обрабатывается фильтром по метаданным, без эмбеддингов.
- **Проверка ответа модели**: если LLM сослалась на статью, которой не было среди найденных фрагментов, ответ отбрасывается.
- **Правильная деградация**: без LLM или при её сбое сервис отвечает 200 и отдаёт цитаты.
- **Наблюдаемость**: по `request_id` из лога можно восстановить промпт, который видела модель.

## Быстрый старт в Docker

```bash
# 1. Исходник Конституции (в git не хранится) — см. «Подготовка исходного текста»
ls data/raw/constitution.txt

# 2. Настройки
cp .env.example .env            # при необходимости отредактировать

# 3. Сборка образа: зависимости и модель эмбеддингов попадают внутрь образа
docker compose build

# 4. Построение индекса в volume
docker compose run --rm api python -m scripts.ingest

# 5. Запуск
docker compose up -d
docker compose ps               # ждём статус (healthy)
curl localhost:8000/readyz
```

Особенности образа:

- модель эмбеддингов скачивается **при сборке**, контейнер стартует без доступа в интернет (`HF_HUB_OFFLINE=1`);
- индекс Chroma хранится в именованном volume `chroma` и переживает пересоздание контейнера (`docker compose down -v` удаляет его);
- исходник подключается с хоста только для чтения;
- процесс работает от непривилегированного пользователя `appuser`;
- один воркер uvicorn: несколько воркеров означают несколько копий модели в памяти и раздельные счётчики rate limit.

Другая модель эмбеддингов собирается параметром сборки, чтобы модель в образе и в настройках не разошлись:

```bash
docker compose build --build-arg EMBEDDING_MODEL=intfloat/multilingual-e5-base
```

При смене модели нужна новая коллекция (`APP_COLLECTION_NAME`) и новый ingest: векторы разных моделей несовместимы, у e5-base они даже другой длины (768 против 384).

Полезные команды:

```bash
docker compose logs -f api                               # логи
docker compose exec api python -m scripts.evaluate       # метрики внутри контейнера
docker compose logs --no-log-prefix api | \
  docker compose exec -T api python -m scripts.replay - --request-id <id>   # промпт запроса
```

## Локальный запуск

Нужны Python 3.13 и [uv](https://docs.astral.sh/uv/).

```bash
uv sync                                         # зависимости, включая dev (pytest)
cp .env.example .env
uv run python -m scripts.prepare_source         # подготовка текста (один раз)
uv run python -m scripts.ingest                 # индекс
uv run uvicorn app.main:app --host 0.0.0.0 --port 8000 --no-access-log
```

`torch` ставится в CPU-сборке из индекса `pytorch-cpu` (см. `pyproject.toml`). Для этого `torch` указан **прямой** зависимостью: `[tool.uv.sources]` действует только на прямые зависимости, и без этого uv поставит CUDA-сборку с пакетами `nvidia-*` на несколько гигабайт.

Чтобы модель не проверяла обновления на Hugging Face при каждом старте (это ~10 секунд сетевых запросов):

```bash
export HF_HUB_OFFLINE=1
```

## Подготовка исходного текста

Текст Конституции берётся из официального источника (pravo.gov.ru, constitution.ru). При копировании в plain text он портится, поэтому сырой файл проходит через `scripts/prepare_source.py`. Пути к сырому и к чистому файлу заданы константами `SRC` и `DST` в начале скрипта; чистый файл должен совпадать с `APP_SOURCE_PATH`.

Что исправляет подготовка:

| проблема в скопированном тексте | как исправляется |
|---|---|
| надстрочные номера потеряны: `Статья 671` | `Статья 67.1` (номер > 137 и оканчивается на 1) |
| составные части: `21.` после части `2.` | `2.1.` |
| составные подпункты: `ж1)`, пункт `"д1"` | `ж.1)`, пункт `"д.1"` |
| редакционные пометки `(В редакции Закона…)`, `(Дополнение частью…)` | удаляются: это история поправок, а не текст нормы |
| заголовки глав и раздела второго на двух строках | склеиваются в одну строку |
| шапка со списком редакций перед преамбулой | удаляется |

Загрузчик (`app/ingest/loader.py`) дополнительно нормализует символы: неразрывные и нулевой ширины пробелы, мягкие переносы, варианты дефисов и кавычек. Используется `NFC`, а не `NFKC`: последний превращает `№` в `No` и искажает цитаты.

После подготовки в тексте 137 статей и 5 составных: 67.1, 75.1, 79.1, 92.1, 103.1.

## Настройки

Все настройки читаются из переменных окружения с префиксом `APP_` или из файла `.env`. **Переменные окружения важнее `.env`.** `.env.example` — только образец, сервис его не читает.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `APP_SOURCE_PATH` | `data/raw/constitution.txt` | подготовленный текст |
| `APP_CHROMA_PATH` | `data/chroma` | папка индекса |
| `APP_COLLECTION_NAME` | `constitution_e5_small_v1` | коллекция; содержит версию модели |
| `APP_EMBEDDING_MODEL` | `intfloat/multilingual-e5-small` | модель эмбеддингов |
| `APP_MIN_CHUNK_CHARS` / `APP_MAX_CHUNK_CHARS` | `200` / `900` | границы длины чанка |
| `APP_CHUNK_HEADER` | `true` | заголовок «Глава… Статья…» в тексте для эмбеддинга |
| `APP_E5_PREFIXES` | `true` | префиксы `query: ` / `passage: ` для e5 |
| `APP_MIN_SCORE` | `0.829` | порог «не найдено», подобран по eval |
| `APP_USE_HYBRID` | `false` | BM25 + RRF (по eval на этом корпусе не помогает) |
| `APP_BM25_STEMMING` | `true` | стемминг для BM25 |
| `APP_LLM_ENABLED` | `false` | включить генерацию ответа |
| `APP_LLM_BASE_URL` | — | адрес OpenAI-совместимого API **с `/v1`** |
| `APP_LLM_MODEL` | `qwen2.5:7b-instruct` | имя модели на сервере |
| `APP_LLM_API_KEY` | `not-needed` | ключ (локальным серверам подходит любой) |
| `APP_LLM_TIMEOUT` / `APP_LLM_MAX_TOKENS` | `30` / `500` | таймаут и лимит ответа |
| `APP_RATE_LIMIT_PER_MINUTE` | `30` | запросов в минуту с одного IP, `0` — без лимита |
| `APP_LOG_LEVEL` | `INFO` | уровень логов |

`APP_CHUNK_HEADER`, `APP_E5_PREFIXES` и параметры чанкования влияют на индекс: после их изменения нужен ingest в новую коллекцию.

## Подключение LLM

Подходит любой сервер с OpenAI-совместимым API: облачный провайдер, Ollama, LM Studio, vLLM.

```ini
APP_LLM_ENABLED=true
APP_LLM_BASE_URL=http://10.11.11.2:1234/v1
APP_LLM_MODEL=qwen/qwen3.5-9b
APP_LLM_TIMEOUT=120
```

Частые проблемы:

- **Нет `/v1` в адресе.** Клиент дописывает `/chat/completions` к `base_url`, и без `/v1` сервер отвечает 404.
- **«Думающая» модель тратит весь лимит на рассуждения.** Признак: `content` пустой, `finish_reason: "length"`, в лог пишется `llm_failed … исчерпала max_tokens`. Решение: отключить рассуждения в настройках модели на сервере (например, в LM Studio) или взять instruct-модель без рассуждений. Настройка хранится на стороне сервера LLM и может сброситься при перезагрузке модели.
- **LLM на той же машине, что и Docker.** Внутри контейнера `localhost` — это сам контейнер; нужен адрес хоста (`host.docker.internal` с `extra_hosts: ["host.docker.internal:host-gateway"]`).

Проверить, видит ли сервис LLM: `curl localhost:8000/readyz` (поле `llm`) и событие `startup` в логе.

Как `/ask` принимает решения:

| ситуация | `found` | `answer` | `citations` | LLM вызывается |
|---|---|---|---|---|
| поиск ниже порога | false | null | [] | нет |
| LLM выключена | true | null | есть | нет |
| модель ответила, ссылки корректны | true | текст | есть | да |
| модель ответила `NOT_FOUND` | false | null | есть | да |
| LLM упала или сослалась на чужую статью | true | null | есть | да, ответ отброшен |

Поле `match` у цитаты показывает, как фрагмент найден: `vector`, `lexical`, `both` (гибрид) или `exact` (точная выборка по номеру статьи, скор в этом случае `null`).

## Как это устроено

```
текст ──► prepare_source ──► loader ──► parser ──► chunker ──► embedder ──► Chroma
                                        (Unit)      (Chunk)     (e5-small)   (cosine)

вопрос ──► санитизация ──► retriever ──► порог ──► [LLM + проверка ссылок] ──► ответ
                              │
                              ├─ «статья N» ─► точная выборка по метаданным
                              └─ вектор (+ BM25 и RRF, если включён гибрид)
```

**Парсер** (`app/ingest/parser.py`) — конечный автомат по строкам: раздел → глава → статья → часть. Подпункты `а)`, `б)` остаются внутри своей части. Пункты раздела второго — единицы без статьи. Номер части — строка, потому что бывают части `2.1`.

**Чанкер** (`app/ingest/chunker.py`):

- у чанка два текста: `embed_text` с заголовком «Глава 1. Основы конституционного строя. Статья 3, часть 1.» идёт в эмбеддинг, `quote` без заголовка показывается пользователю;
- части короче 200 символов сливаются со следующими частями той же статьи (`Статья 3, части 1-2`), но никогда не через границу статьи;
- части длиннее 900 символов режутся по границам предложений (с учётом `;` и подпунктов) с перекрытием в одно предложение;
- id детерминированные: `art-3-p-1`, `art-5-p-1..3` (слияние), `art-72-p-1-c2` (кусок разрезанной части).

**Индекс** (`app/search/store.py`): Chroma с косинусной метрикой, заданной при создании коллекции. Chroma возвращает расстояние, сервис переводит его в близость: `score = 1 - distance`. `ingest` идемпотентен и удаляет «осиротевшие» чанки, чьих id больше нет после смены параметров чанкования. В метаданных хранится `seq` — порядок чанка в документе.

**Эмбеддинги** (`app/search/embedder.py`): `multilingual-e5-small` с префиксами `query: ` и `passage: `, нормализованные векторы, LRU-кеш запросов.

**Ретривер** (`app/search/retriever.py`):

1. если в вопросе названа статья («статья 15», «ст. 67.1») — точная выборка по метаданным;
2. векторный поиск 30 кандидатов;
3. если лучший косинус ниже `min_score` — «не найдено»;
4. если включён гибрид — BM25 по `ref + quote` и слияние через Reciprocal Rank Fusion.

**Генерация** (`app/llm/`): промпт ограничивает источник фрагментами, требует ссылку после каждого утверждения, задаёт ответ `NOT_FOUND`, запрещает толкования и помечает документы и вопрос как данные. `temperature=0`. Ответ проверяется: ссылка на статью, которой нет среди найденных фрагментов, означает, что модель взяла сведения «из головы», и такой ответ не отдаётся.

## Оценка качества

Набор: `eval/questions.csv`, 39 позитивных и 9 негативных вопросов. Позитивные сформулированы бытовым языком и юридическими терминами. Негативные включают трудные вопросы из соседних правовых областей: исковая давность, испытательный срок, размер пособия по безработице.

```bash
uv run python -m scripts.evaluate --tag "baseline"
APP_USE_HYBRID=true uv run python -m scripts.evaluate --tag "с BM25"
```

Метрики ранжирования считаются без порога. **Зазор** — разница между худшим скором позитивного вопроса и лучшим скором негативного: чем он больше, тем надёжнее порог «не найдено». Refusal accuracy — при пороге, подобранном для каждой конфигурации отдельно: у разных конфигураций разная шкала скоров, и общий порог сравнивал бы шкалы, а не качество.

| Эксперимент | recall@1 | recall@3 | recall@5 | MRR | зазор | свой порог | refusal acc | false refusal |
|---|---|---|---|---|---|---|---|---|
| **baseline** (без BM25) | 97.4% | 100.0% | 100.0% | 0.987 | +0.020 | 0.829 | 100% | 0% |
| с BM25 | 92.3% | 97.4% | 97.4% | 0.949 | +0.020 | 0.829 | 100% | 0% |
| с BM25 без стемминга | 89.7% | 94.9% | 97.4% | 0.929 | +0.020 | 0.829 | 100% | 0% |
| без заголовка в embed_text | 100.0% | 100.0% | 100.0% | 1.000 | +0.004 | 0.825 | 100% | 0% |
| без префиксов e5 | 100.0% | 100.0% | 100.0% | 1.000 | +0.001 | 0.841 | 100% | 0% |
| чанки до 500 символов | 92.3% | 100.0% | 100.0% | 0.962 | +0.013 | 0.833 | 100% | 0% |
| чанки до 1500 символов | 97.4% | 100.0% | 100.0% | 0.987 | +0.020 | 0.829 | 100% | 0% |
| без слияния коротких частей | 94.9% | 100.0% | 100.0% | 0.974 | +0.020 | 0.829 | 100% | 0% |
| e5-base | 100.0% | 100.0% | 100.0% | 1.000 | +0.009 | 0.814 | 100% | 0% |

### Выводы

- **Ранжирование на этом наборе почти насыщено**: recall@5 = 100% у всех конфигураций без BM25, разница в recall@1 — 1–2 вопроса, то есть в пределах шума. Различает конфигурации в первую очередь зазор.
- **Префиксы e5 и заголовок в `embed_text`** почти не влияют на ранжирование, но сильно влияют на зазор: 0.001 и 0.004 без них против 0.020 с ними. Без префиксов модель почти не отличает правовой вопрос без ответа от вопроса с ответом.
- **BM25 ухудшает ранжирование.** На перефразированных вопросах он находит случайные совпадения слов: для «Может ли кто-то войти в мою квартиру без моего согласия?» он поднимает ст. 24 («без его согласия») выше ст. 25 («Жилище неприкосновенно…»), у которой с вопросом нет ни одного общего слова, а RRF награждает такое «согласие» двух методов. Терминологические вопросы вектор находит и без BM25, а запросы по номеру статьи, ради которых BM25 был нужен, обрабатывает точная выборка. Гибрид выключен по умолчанию, код сохранён: при расширении корпуса эксперимент нужно повторить.
- **Размер чанков почти не важен**: части Конституции короткие, и лимит длины затрагивает лишь несколько статей (71, 72, 83). До 500 символов немного хуже: мелкая нарезка рвёт смысл.
- **Слияние коротких частей** немного помогает ранжированию.
- **e5-base** не лучше e5-small по ранжированию, хуже по зазору, втрое медленнее при индексации (20.5 с против 5.8 с) и втрое тяжелее.

Итоговая конфигурация: e5-small, префиксы и заголовок включены, BM25 выключен, чанки 200–900 символов со слиянием, `min_score = 0.829`.

### Ограничения оценки

- Набор маленький: один вопрос — 2.6 п.п. recall, а зазор определяется двумя крайними вопросами. На наборе из 37 вопросов e5-base давала лучший зазор, а после добавления двух трудных негативов — худший.
- Набор лёгкий для ранжирования; чтобы метрики снова различали конфигурации, нужны вопросы, ответ на которые распределён по нескольким статьям или лежит в длинных статьях.
- Зазор 0.020 невелик: на реальных вопросах порог иногда будет ошибаться. Вторым рубежом служит LLM с ответом `NOT_FOUND`.
- Порог, подобранный на лёгких негативах, выглядит надёжнее, чем есть: два трудных вопроса сдвинули максимум негативных скоров с 0.805 до 0.820.

## Логи и наблюдаемость

Каждый запрос получает `request_id` (из заголовка `X-Request-ID` или сгенерированный). Он возвращается в ответе и через `ContextVar` попадает во все строки лога этого запроса, включая логи сторонних библиотек и код, выполняемый в пуле потоков.

События пишутся одной JSON-строкой. Событие `ask`:

```json
{"event": "ask", "request_id": "test-1", "found": true, "total_ms": 1825,
 "embed_ms": 39, "search_ms": 2, "best_score": 0.8566, "route": "vector",
 "question": "Кто источник власти в РФ?", "k": 5, "suspicious": false,
 "prompt_version": "ask-v1",
 "hits": [{"id": "art-3-p-1..2", "score": 0.8566, "match": "vector"}, "..."],
 "llm_status": "ok", "llm_ms": 1782, "answer": "..."}
```

- `route` объясняет результат поиска: `exact`, `vector`, `hybrid`, `refused` (ниже порога), `empty`;
- `llm_status`: `skipped`, `disabled`, `ok`, `not_found`, `bad_citations`, `error`;
- тайминги показывают, что LLM занимает ~97% времени ответа, а эмбеддинг и поиск — десятки миллисекунд;
- `suspicious` — флаг похожести вопроса на prompt injection, только для мониторинга, ничего не блокирует.

Восстановить промпт, который видела модель:

```bash
uv run uvicorn app.main:app --host 0.0.0.0 --port 8000 --no-access-log 2>&1 | tee service.log
uv run python -m scripts.replay service.log --request-id test-1
```

Скрипт берёт фрагменты из индекса по id из лога и собирает промпт той же функцией, что и сервис. Он предупреждает, если с момента запроса изменилась версия промпта или индекс был пересобран.

В логах хранятся вопросы пользователей. В реальной эксплуатации такие логи нужно защищать, ограничивать срок их хранения или маскировать персональные данные.

**Rate limit**: скользящее окно в памяти, 30 запросов в минуту с IP, ответ 429 с `Retry-After`. `/healthz` и `/readyz` не ограничиваются. Ограничения: счётчик живёт в памяти одного процесса (для нескольких воркеров или реплик нужен общий, например Redis), а за обратным прокси реальный IP нужно брать из доверенного `X-Forwarded-For`.

## Защита от prompt injection

Защита устроена слоями, и важно понимать, какой слой что даёт:

1. **Устройство промпта** (основное): документы и вопрос размечены тегами как данные, модели запрещено выполнять инструкции из них.
2. **Проверка ответа** (основное): ссылки на статьи, которых не было среди фрагментов, отбрасываются. В худшем случае пользователь увидит странный пересказ реальных фрагментов, а цитаты всё равно берутся из базы.
3. **Порог «не найдено»**: вопросы вне темы вообще не доходят до модели.
4. **Санитизация** (вспомогательное): удаляются управляющие символы, разметка ролей (`system:`) и наши собственные теги (`</вопрос>`), чтобы пользователь не мог «выйти» из блока данных.
5. **Флаг `suspicious`** (только мониторинг): регулярками атаку не распознать надёжно, а блокировка по ним задела бы честные вопросы вроде «Может ли суд игнорировать закон?».

Проверка ответа ловит ссылки на чужие статьи, но не ловит неверный пересказ правильной статьи.

## Известные ограничения

- Корпус — только Конституция; при добавлении других документов нужно повторить эксперименты (особенно с BM25) и добавить в метаданные поле документа.
- Порог «не найдено» подобран на небольшом наборе и может ошибаться на реальных вопросах.
- Rate limit и кеш запросов живут в памяти одного процесса.
- LLM на CPU отвечает секунды; ответ целиком ждёт генерации (без стриминга).
