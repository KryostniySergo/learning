# auth-service

Регистрация компаний и сотрудников, аутентификация, личные данные. Здесь же живёт
оркестратор саги онбординга и сторож зависших саг.

## Запуск

В составе всей системы: `docker compose up` из корня проекта.

Локально (требуется поднятый `auth-db` и `kafka`):

```bash
uv sync
cp .env.example .env
uv run alembic upgrade head
uv run uvicorn app.main:app --reload --port 8000
uv run python -m app.outbox.run_publisher   # в отдельном терминале
uv run python -m app.saga.run_saga          # в отдельном терминале
uv run python -m app.saga.run_watchdog      # в отдельном терминале
```

## Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DB_HOST` | `localhost` | Хост Postgres |
| `DB_PORT` | `5432` | Порт Postgres |
| `DB_NAME` | `auth_db` | Имя базы |
| `DB_USER` | `postgres` | Пользователь |
| `DB_PASS` | — обязательна | Пароль |
| `KAFKA_BOOTSTRAP_SERVERS` | `localhost:9092` | Адрес брокера |
| `KAFKA_TOPIC` | `auth-events` | Топик доменных событий |
| `KAFKA_SAGA_COMMANDS_TOPIC` | `saga-commands` | Топик команд саги |
| `KAFKA_SAGA_REPLIES_TOPIC` | `saga-replies` | Топик ответов саги |
| `KAFKA_DLQ_TOPIC` | `dlq` | Топик для неотправленных сообщений |
| `OUTBOX_MAX_RETRIES` | `5` | Число попыток публикации до DLQ |
| `OUTBOX_RETRY_BASE_SECONDS` | `2` | База экспоненциальной задержки ретраев |
| `SAGA_TIMEOUT_SECONDS` | `300` | Через сколько сага считается зависшей |
| `SAGA_WATCHDOG_INTERVAL_SECONDS` | `60` | Период проверки зависших саг |
| `JWT_SECRET` | — обязательна | Общий секрет подписи токенов |
| `JWT_ALGORITHM` | `HS256` | Алгоритм подписи |
| `JWT_EXPIRE_MINUTES` | `60` | Время жизни токена |
| `SMTP_HOST` | `localhost` | Хост SMTP (MailHog) |
| `SMTP_PORT` | `1025` | Порт SMTP |
| `SMTP_FROM` | `noreply@company-system.local` | Адрес отправителя |
| `PRODUCER_NAME` | `auth-service` | Имя в поле `producer` конверта |

У `DB_PASS` и `JWT_SECRET` нет значений по умолчанию: без них сервис не стартует.
Это сделано намеренно, чтобы запуск с секретом из репозитория был невозможен.

## Эндпоинты

Базовый префикс: `/auth/api/v1`

### Регистрация компании

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/check_account/{account}` | Проверяет, свободна ли почта; создаёт инвайт и отправляет код |
| `POST` | `/sign-up/` | Подтверждает владение почтой по токену |
| `POST` | `/sign-up-complete/` | Создаёт компанию и администратора, задаёт пароль |

### Аутентификация

| Метод | Путь | Описание |
|---|---|---|
| `POST` | `/login/` | Выдаёт JWT. Необязательный `company_id` выбирает компанию |

### Сотрудники

| Метод | Путь | Доступ | Описание |
|---|---|---|---|
| `POST` | `/employees/` | admin | Заводит сотрудника, отправляет инвайт. Необязательные `struct_adm_id` и `position_id` определяют место в оргструктуре и запускают сагу онбординга после регистрации |
| `POST` | `/employees/register/` | без токена | Завершает регистрацию по инвайту |

### Личные данные

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/me/` | Имя, фамилия и привязанная почта |
| `PATCH` | `/me/` | Меняет имя и фамилию, публикует `employee.updated` |
| `POST` | `/me/email/` | Запускает смену почты: код уходит на новый адрес |
| `POST` | `/me/email/confirm/` | Подтверждает новый адрес и переключает на него вход |

Небезопасные операции принимают необязательный заголовок `Idempotency-Key`:
повторный запрос с тем же ключом вернёт сохранённый ответ вместо нового эффекта.

## Модель данных

| Таблица | Назначение |
|---|---|
| `account` | Зарегистрированные почты |
| `user` | Пользователи (имя, фамилия) |
| `member` | Членство пользователя в компании с ролью |
| `company` | Компании |
| `invite` | Приглашения с токеном, сроком и целевым подразделением |
| `secrets` | Связь user↔account и хеш пароля |
| `saga_instance` | Состояние запущенных саг |
| `idempotency_key` | Сохранённые ответы небезопасных операций |
| `outbox_message` | Исходящие события |
| `inbox_message` | Отметки об обработанных входящих событиях |

Почта, пользователь и пароль разнесены по трём таблицам, потому что появляются на
разных шагах регистрации: `account` создаётся, когда пользователя ещё нет, а
`secrets` — только когда задан пароль.

Роль хранится в `member`, а не в `user`: это свойство членства в конкретной компании,
а не самого человека. Поэтому один человек может состоять в нескольких компаниях
с разными ролями.

На `account.email` стоит **частичный** уникальный индекс — только среди записей
с `deleted_at IS NULL`. При смене почты старый аккаунт помечается удалённым,
и адрес освобождается для повторной регистрации.

## Статусы инвайта

```
CREATED ──▶ IN_PROGRESS ──▶ COMPLETED
   │             │
   └──────┬──────┘
          ▼
       FAILED
```

Переход проверяется на каждом шаге: нельзя пропустить подтверждение почты или
использовать инвайт дважды. Регистрация сотрудника по приглашению идёт
`CREATED → COMPLETED`, минуя промежуточный шаг.

## Сага онбординга

Оркестратор (`app/saga/onboarding_saga.py`) слушает `employee.registered`, ведёт
состояние в `saga_instance` и командует исполнителями через топик `saga-commands`.
Подробное описание сценария и компенсаций — в корневом README.

Сторож (`app/saga/watchdog.py`) отдельным процессом ищет саги, зависшие без ответа
дольше `SAGA_TIMEOUT_SECONDS`, и запускает для них компенсацию.
