# Большое задание: система управления и контроля бизнеса (микросервисы)

## О чём задание

Нужно спроектировать и реализовать backend-приложение — **систему управления бизнесом**.
Приложение делится на **микросервисы**, общающиеся через **Kafka**. Это финальный проект, в котором
собираются вместе все изученные темы: FastAPI, SQLAlchemy, PostgreSQL, миграции, Docker, брокер
сообщений и продуктовые паттерны бэкенда.

Оценивается не только «работает ли», но и **архитектура**: чистое разделение слоёв, корректная
работа с транзакциями и событиями, применение паттернов.

> Это учебный проект. Делайте его поэтапно (см. раздел «Этапы»), не пытайтесь написать всё сразу.
Лучше меньше сервисов, но с правильной архитектурой, чем всё и «на коленке».

## Архитектура (обязательные требования)

1. **Минимум 3 микросервиса** (монолит не принимается):
    - `auth-service` — регистрация, аутентификация, личные данные сотрудника;
    - `org-service` — организационная структура (подразделения, должности);
    - `tasks-service` — задачник.
2. **Kafka — брокер сообщений** между сервисами. Синхронные HTTP-вызовы между сервисами
допускаются только там, где событийная модель неудобна, и должны быть обоснованы.
3. **У каждого сервиса — своя БД** (PostgreSQL). Сервисы **не ходят в чужие таблицы** напрямую,
только через API/события. (Допустимо разделение через схемы в одном инстансе Postgres, но
логически базы изолированы.)
4. **Transactional Outbox** — обязателен: смена бизнес-состояния и публикация события происходят
в одной транзакции.
5. **Idempotent Consumer / Inbox** — обязателен: повторная доставка события не приводит к повторному
эффекту.
6. Всё поднимается одной командой через **docker-compose** (сервисы + Postgres + Kafka + Zookeeper/KRaft).

Схема потоков (пример):

```
             ┌────────────┐      события      ┌────────────┐
   client →  │ auth-svc   │ ───(outbox)──────▶│   Kafka    │
             └────────────┘                    └─────┬──────┘
                                                     │  (inbox)
                                        ┌────────────┴─────────────┐
                                        ▼                          ▼
                                 ┌────────────┐            ┌────────────┐
                                 │  org-svc   │            │ tasks-svc  │
                                 └────────────┘            └────────────┘
```

## Обязательные паттерны (чек-лист)

Каждый пункт должен быть реально применён и его нужно уметь показать в коде:

- [ ]  **Repository** — доступ к данным спрятан за репозиториями.
- [ ]  **Service Layer** — бизнес-логика в сервисах, вьюхи тонкие.
- [ ]  **Unit of Work** — сессия на запрос + единая граница транзакции (commit/rollback).
- [ ]  **Dependency Injection** — граф зависимостей собран декларативно (не `new` внутри логики).
- [ ]  **DTO / Schema** — Pydantic-схемы отделены от ORM-моделей (Request/Response разнесены).
- [ ]  **Router Composition** — доменные роутеры + версионирование (`/api/v1`).
- [ ]  **Depends для сквозных задач** — auth, сессия, пагинация как переиспользуемые зависимости.
- [ ]  **Idempotency** — небезопасно-повторяемые операции защищены идемпотентным ключом.
- [ ]  **Centralized Error Handling** — доменные исключения маппятся в HTTP в одном месте.
- [ ]  **Transactional Outbox** — надёжная публикация событий.
- [ ]  **Idempotent Consumer / Inbox** — защита от дублей на стороне потребителя.
- [ ]  **Adapter / Gateway** — работа с Kafka спрятана за обёртками (продюсер/консьюмер).
- [ ]  **Saga / Orchestrator** — хотя бы один распределённый сценарий с компенсацией.
- [ ]  **Event Contracts** — типы событий, envelope и версии зафиксированы.

## Сервис 1. `auth-service` — регистрация и личные данные

### 1.1. Аутентификация и авторизация

Все запросы к сервисам проходят через middleware/зависимость, проверяющую пользователя и его права.
Используйте **JWT** (готовое решение) либо собственную реализацию токенов. Права как минимум двух
уровней: **администратор компании** и **обычный сотрудник**.

### 1.2. Регистрация компании (по почте)

Трёхшаговый флоу:

1. **Проверка почты** — `GET /auth/api/v1/check_account/{account}`
Свободна ли почта. Если валидна — генерируем инвайт и «отправляем» код на почту
(для учебного проекта: логировать код / писать в консоль / MailHog).
2. **Подтверждение почты** — `POST /auth/api/v1/sign-up/`
    
    ```json
    { "account": "user@example.com", "invite_token": "..." }
    ```
    
    Если аккаунт и инвайт валидны — разрешаем перейти к завершению регистрации.
    
3. **Завершение регистрации** — `POST /auth/api/v1/sign-up-complete/`
    
    ```json
    {
      "account": "user@example.com",
      "pass": "...",
      "first_name": "...",
      "last_name": "...",
      "company_name": "..."
    }
    ```
    
    Создаём **компанию** и **сотрудника-администратора** (главного редактора) этой компании.
    Администратор в дальнейшем может создавать сотрудников и генерировать инвайты.
    

### 1.3. Регистрация сотрудника

- Администратор заранее создаёт сотрудника и привязывает его к компании.
- Генерируется инвайт, привязанный к пользователю и почте.
- На почту приходит ссылка; по ней сотрудник подтверждает регистрацию, вводя пароль.

### 1.4. Личные данные сотрудника

- Перепривязать почту (со сменой/подтверждением).
- Сменить имя и фамилию.

### 1.5. События, которые публикует сервис (в Kafka, через outbox)

Например: `company.created`, `employee.created`, `employee.registered`,
`employee.email_changed`. Их слушают `org-service` и `tasks-service`, чтобы знать о пользователях
и компаниях (реплика справочных данных у себя).

## Сервис 2. `org-service` — организационная структура

Организационная структура привязана к компании и хранит: подразделения (вложенная иерархия),
должности, кто на какой должности, роли в подразделении, руководителей и подчинённых.
См. что такое орг. структура: концепция «дерева» подразделений компании.

### Функционал

- **Подразделения вложенной структуры** — реализовать через **`ltree` в PostgreSQL** (деревья).
- **Создание должностей.**
- **Привязка должностей к сотрудникам и подразделениям.**
- **Назначение руководителей подразделений.**
- **Редактирование и удаление** подразделений и должностей (с корректной обработкой поддеревьев).

### Требования

- Иерархия строится и запрашивается через `ltree` (поддеревья, предки, потомки).
- Данные о сотрудниках приходят из `auth-service` **через события** (свою «реплику» пользователей
сервис ведёт сам; в чужую БД не ходит).
- Все операции требуют авторизации; менять структуру может администратор компании.

## Сервис 3. `tasks-service` — задачник

### Функционал

Создание, редактирование, удаление задачи. Задача хранит:

| Поле | Тип |
| --- | --- |
| Заголовок | string |
| Описание | text |
| Автор | user |
| Ответственный | user |
| Наблюдатели | list[user] |
| Исполнители | list[user] |
| Дедлайн | datetime |
| Статус | enum |
| Оценка времени на выполнение | duration/минуты |

### Требования

- Пользователи (автор/ответственный/наблюдатели/исполнители) валидируются по «реплике» пользователей,
полученной из событий `auth-service`.
- Смена статуса задачи публикует событие (`task.status_changed`) — пригодится для саги/уведомлений.
- Доступ к задачам ограничен компанией пользователя.

## Межсервисное взаимодействие и контракты событий

- Все события идут через Kafka в формате **envelope** (единый конверт): `event_id`, `event_type`,
`aggregate_id`, `occurred_at`, `payload`, `schema_version`, `correlation_id`, `causation_id`,
`producer`.
- Типы событий зафиксированы в enum (единый источник правды), payload — версионируемая схема.
- Дедупликация — по детерминированному `dedup_key` (в outbox) и по `(consumer_name, event_id)`
(в inbox).
- Партиционирование по `aggregate_id`, чтобы события одной сущности шли по порядку.

### Обязательный распределённый сценарий (Saga)

Реализуйте **минимум один** сквозной процесс через несколько сервисов с компенсацией. Пример:

> **Онбординг сотрудника.** `auth-service` завершает регистрацию сотрудника → событие
`employee.registered` → `org-service` привязывает его к подразделению/должности по инвайту →
`tasks-service` создаёт «приветственную» задачу. Если один из шагов не удался (например,
должность уже занята/удалена) — запускается **компенсация**: откат привязки и пометка инвайта как
недействительного. Все переходы — через оркестратор с проверкой статуса (guard).

## Модель данных (ориентир)

Схема — рекомендация, детали можно адаптировать. Таблицы распределяются по сервисам.

**auth-service:**
- `user` — пользователи;
- `account` — зарегистрированные почты;
- `invite` — инвайты;
- `secrets` — связь user↔︎account + хранение пароля (хеш!);
- `credentials` — api_key для входа;
- `company` — компании;
- `members` — связь пользователь↔︎компания (+ роль).

**org-service:**
- `position` — должности;
- `users_positions` — связь пользователь↔︎должность;
- `struct_adm` — узлы орг. структуры (**`ltree`** для дерева);
- `struct_adm_positions` — связь подразделение↔︎должности.

**tasks-service:**
- `task`, `task_watchers`, `task_assignees`, реплика `users`.

Плюс в **каждом** сервисе: `outbox_messages` и `inbox_messages`.

> Пароли — только в виде хеша (bcrypt/argon2). Секреты — через `.env`, не в коде.

## Этапы сдачи (рекомендуемый порядок)

Сдавайте по этапам — так проще ревьюить и не утонуть.

1. **Каркас.** Монорепо/несколько репо, `docker-compose` с Postgres и Kafka, скелеты трёх сервисов
(FastAPI + структура папок: `api/`, `services/`, `repositories/`, `models/`, `schemas/`),
Alembic, Poetry, Ruff, логирование.
2. **auth-service (основа).** Модели, регистрация компании (3 шага), JWT-аутентификация, middleware
авторизации, личные данные. Слои Repository/Service/UoW, DI, DTO, централизованные ошибки.
3. **Outbox + Kafka.** Публикация событий из auth (`company.created`, `employee.*`) через
transactional outbox + публикатор. Adapter над Kafka.
4. **org-service.** Inbox-консьюмер (реплика пользователей), орг. структура на `ltree`, CRUD
подразделений/должностей, руководители.
5. **tasks-service.** Задачник (CRUD), реплика пользователей через inbox, события смены статуса.
6. **Saga.** Сквозной сценарий онбординга с компенсацией (оркестратор), идемпотентные консьюмеры, DLQ.
7. **Идемпотентность и полировка.** Idempotency-Key на небезопасных операциях, тесты, README.

## Подсказки, чтобы не застрять

- Начинайте с **одного** сервиса целиком (auth) со всеми слоями — дальше это шаблон для остальных.
- Outbox/inbox сделайте **переиспользуемым модулем** — он одинаков во всех сервисах.
- Реплику пользователей в org/tasks держите **минимальной** (id, имя, компания) — только то, что
реально нужно для проверок.
- Сначала «счастливый путь», потом — сбои/компенсации/ретраи.
-
